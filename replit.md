# FisioGest Pro

## Overview

FisioGest Pro is a comprehensive SaaS clinic management platform for physiotherapists, aestheticians, and Pilates instructors. It provides electronic health records, scheduling, financial management, reporting, and COFFITO compliance. The platform aims to be a modern, efficient, and user-friendly solution, prioritizing usability and data integrity.

The project is a pnpm monorepo hosted on Replit, consisting of a frontend, an API, and a mockup-sandbox, all served via Replit's shared reverse proxy.

**Default Localization:**
- **Language**: Brazilian Portuguese (pt-BR)
- **Currency**: Brazilian Real (BRL — R$)
- **Measurements**: International System (SI) — kg, cm, °C
- **Date Format**: dd/MM/yyyy
- **Time Format**: HH:mm (24 hours)
- **Decimal Separator**: comma (`,`)
- **Thousands Separator**: dot (`.`)
- **Default Time Zone**: America/Sao_Paulo (UTC-3 / UTC-2 during daylight saving)

## User Preferences

Always import `useAuth` from `@/hooks/use-auth`. The `auth-context.tsx` exports only `AuthProvider` and `AuthContext`. The `useAuth` hook now exposes `refreshUser()` to refetch `/api/auth/me` and update the user in context (e.g., after LGPD policy acceptance, so the modal doesn't reappear on every page navigation).

Before adding any new dependency, confirm that it is compatible with Node 22, ESM, and pnpm workspaces. Before proposing a framework migration, validate that the target is within the official compatibility matrix.

**Important (backend):** Never use `new Date().toISOString()` or `new Date().getMonth()` for business calculations. Always use the functions in `artifacts/api-server/src/lib/dateUtils.ts`:
- `todayBRT()` → "YYYY-MM-DD" string in Brasília timezone
- `nowBRT()` → `{ year, month, day }` in Brasília timezone
- `monthDateRangeBRT(year, month)` → `{ startDate, endDate }` for a month

**System Design Choices:**

**Scheduler (Background Jobs):**
- **Billing Automation**: Handles recurring monthly charges.
- **Consolidated Invoice Generation**: Creates unique monthly invoices.
- **Auto-confirmation**: Confirms appointments.
- **End-of-Day Closure**: Manages no-show, absence fees, and auto-completion.
- **Subscription Check**: Manages expired trials and overdue accounts.
- **Slot Hold Cleanup**: Periodically purges expired slot reservations to prevent double-booking.

**Financial Core:**
- Formal double-entry accounting ledger for financial records.
- Revenue recognition upon service delivery or credit/wallet consumption.
- Payment cascades for consolidated invoices ensure accurate revenue recognition.
- Robust audit trails for reversals with mandatory `reversalReason`.
- Accounting categorization by procedure via `procedures.accounting_account_id`.
- Advanced accounting for deferred receivables, including partial reversals for cancellations.

**Treatment Plan as Formal Sale:**
- Plan acceptance (`POST /api/patients/:patientId/treatment-plans/:planId/accept`) generates a snapshot of prices and captures LGPD trail data.
- Remote acceptance via public link is supported.
- Idempotent and transactional financial effects upon plan acceptance, creating invoices and session credits.
- Lazy generation of monthly plan invoices.
- **Atomic Acceptance & Materialization Orchestrator**: Ensures that plan acceptance, financial record creation, and appointment materialization are completed as a single, consistent operation. Includes compensatory rollback if materialization fails.
- **Initial scheduling cap**: `weekDays` per plan item cannot exceed `sessionsPerWeek` at initial setup.
- **Per-day start times**: Supports different start times per weekday for plan items, persisting as a JSON map.

**Quantitative Limits Enforcement (SaaS Plans):**
- Middleware `enforceLimit(resource, options?)` prevents actions if SaaS plan limits (e.g., `maxPatients`, `maxUsers`) are exceeded, returning `402 Payment Required`.

**LGPD Compliance:**
- Versioned policy documents and user acceptance records.
- Backend endpoints for policy retrieval, acceptance, and patient data export.
- Frontend features for policy acceptance and patient data export.

**Architectural Conventions:**
- **Backend (`modules/<domain>/<feature>/`):** Organized by `routes.ts`, `service.ts`, `repository.ts`, `schemas.ts`, etc.
- **Frontend (`pages/<domain>/<feature>/`):** Organized by `index.tsx`, `components/`, `hooks/`, `schemas/`.
- **Zod Shared Schemas**: Centralized in `src/schemas/`.
- **HTTP Call Layer**: Uses `src/utils/api.ts` helpers for consistent authentication and error handling.
- **Import Conventions**: Specific aliases for Orval-generated hooks, shared types, and authentication hooks.

**Observability:**
- **Backend Logger**: `lib/logger.ts` (pino + AsyncLocalStorage) with `requestId` and redaction.
- **Correlation ID**: `requestContext.ts` middleware generates/propagates `X-Request-Id`.
- **Sentry**: Optional integration.
- **Scheduler**: Each CRON job is instrumented with duration logging and exception capture.

## Replit Environment

**Running on Replit** — pnpm monorepo migrated and confirmed working.

**Workflow:** `Start application` runs `pnpm run dev`, which:
1. Builds shared libs (`tsc --build`)
2. Starts API server on port **8080** via `tsx`

- `JWT_SECRET` — JWT signing key
- `CLOUDINARY_URL` — Cloudinary media storage
- `ASAAS_API_KEY` — Asaas billing integration

**Deployment:** `pnpm run build` then `pnpm run start` (runs `node artifacts/api-server/dist/index.cjs` which serves the built SPA from `artifacts/fisiogest/dist/public`).

## Cross-Clinic Patient Identity

Implemented in migration `0021_patient_cross_clinic.sql`:

- **`patients.cpf` uniqueness**: global UNIQUE removed; replaced with `UNIQUE(cpf, clinic_id)` so the same CPF can exist across multiple clinics.
- **`patients.source_patient_id`**: nullable self-reference FK pointing to the original record in the source clinic.
- **`patient_access_requests` table**: tracks requests from one clinic to another for clinical data access (`scope: clinical_records`), with `status: pending | approved | denied`.

**Backend routes (`/api/patients`):**
- `POST /` — detects CPF in another clinic → returns `409 { code: "CPF_EXISTS_OTHER_CLINIC", patient, sourceClinic }`.
- `POST /import-by-cpf` — copies basic demographic fields from the source record into the requesting clinic.
- `PUT /:id` — after a demographic update, syncs `name, phone, email, birthDate, address, profession, emergencyContact` to all records sharing the same CPF across other clinics (`notes` is clinic-specific and is NOT synced).
- `POST /access-requests` — send a clinical-data access request to the source clinic.
- `GET /access-requests/incoming` — list pending requests for the current clinic (as source).
- `GET /access-requests/outgoing` — list requests sent by the current clinic.
- `PATCH /access-requests/:id` — approve or deny a pending request (source clinic only).

**Frontend:**
- `CreatePatientForm` (patients list page): on 409 `CPF_EXISTS_OTHER_CLINIC`, hides the normal form and shows an amber import banner with the existing patient's data and an "Import basic data" button.
- `AccessRequestsPanel` (patient detail sidebar): invisible when there are no pending requests; shows a card per pending request with approve/deny buttons.
